# Intentional differences from LoopFollow for iOS

The Android app follows the iOS app feature by feature. Where it behaves differently on purpose, the code says so with a comment that starts with `ANDROID-DEVIATION:`, and the difference is listed here. When an iOS change is brought over, check this list and `grep -rn "ANDROID-DEVIATION" app/src` first, so a deliberate difference is not synced away.

Each entry: **title**: what differs and why. Code: Android location. iOS: the counterpart to compare against.

## Platform

- **No APNs on Android**: the app cannot receive push notifications from Trio or Loop. Everything that depends on a push reaching LoopFollow is covered by the entries below. Code: `remote/`. iOS: `Remote/ReturnNotificationInfo+LoopFollow.swift`.
- **No LoopFollow Apple team**: the Android app has no team ID or APNs key of its own, so remote commands always sign with the APNs key and key ID entered in Remote Settings (the iOS "team IDs differ" case), and those fields are always shown. The `apns` import/export section is still read and written, including its optional `teamId`, so QR codes stay compatible. When an import carries an `apns` key and the Remote Settings key is empty, that key fills the Remote Settings fields if its team matches the Loop/Trio team or either team is unknown; a key of another team is left out and the import result says so. A send that lacks part of the setup names the missing items and where each comes from. Code: `remote/TrioRemote.kt`, `remote/loop/LoopAPNSService.kt`, `remote/APNS.kt` (`RemoteSetupMessage`), `ui/remote/RemoteSettingsScreen.kt`, `settings/importexport/ExportableSettings.kt` (`RemoteKeyAdoption`), `ui/settings/importexport/ImportExportSettingsViewModel.kt`. iOS: `Remote/Settings/RemoteSettingsViewModel.swift` (`areTeamIdsDifferent`), `RemoteShared/WatchCredentials.swift` (`RemoteSigningKey.resolve`).
- **No LF Hub push**: Android cannot receive APNs, so it never registers a push token or key with a hub (`PUT /v1/device/apns`) and gets no hub badge, Live Activity or alarm pushes. A hub never hands out APNs keys or remote secrets; remote commands are set up through Remote Settings or the settings QR code. iOS: `Hub/HubClient.swift`.
- **Background execution**: a foreground service with an ongoing glucose notification, a partial wake lock and a 6-minute watchdog alarm keep data downloads and alarms running. iOS uses background audio/refresh. Code: `service/LoopFollowService.kt`. iOS: `BackgroundRefresh/`.
- **Alarm sound**: played as an alarm-stream `MediaPlayer`, with the volume override applied to the alarm stream. Code: `alarm/AlarmSound.kt`. iOS: `Controllers/AlarmSound.swift`.
- **Volume button snooze**: a press is a volume key event while LoopFollow is in front, and a system volume-changed broadcast otherwise, since that broadcast is the only signal a background app gets; a press at the end of the volume range changes nothing and is not seen, as on iOS. Bluetooth/CarPlay play-pause buttons do not snooze. Code: `alarm/VolumeButtonSnooze.kt`, `ui/MainActivity.kt` (`dispatchKeyEvent`). iOS: `Controllers/VolumeButtonHandler.swift`.
- **Device owner authentication**: biometrics or the screen-lock PIN/pattern/password (`BIOMETRIC_WEAK | DEVICE_CREDENTIAL`). Code: `remote/RemoteSupport.kt` (`AuthService`). iOS: `Helpers/AuthService.swift`.

- **App icon**: an adaptive icon made from the iOS `1024.png` (scaled to the 72 dp viewport, so the ring keeps its iOS proportions) over the same light gradient, plus a monochrome layer from `1024-tinted.png` for themed icons. The launcher decides the mask shape (a circle on Pixel). Regenerate the layers with `tools/make_icon.py` when the iOS icon changes. Code: `app/src/main/res/mipmap-*/ic_launcher_*.png`, `res/mipmap-anydpi-v26/`, `res/drawable/ic_launcher_background.xml`. iOS: `LoopFollow/Resources/Assets.xcassets/AppIcon.appiconset/`.

- **Lock screen**: the app shows over the lock screen and turns the screen on only while an alarm is active, and then only its Snoozer; everything else (settings, remote commands, secrets) needs the phone unlocked. iOS apps never show over the lock screen. Code: `ui/MainActivity.kt`, `AndroidManifest.xml`. iOS: none.
- **Secrets encrypted at rest, no backup or transfer**: the Nightscout token, Dexcom Share password, both APNs keys, the Trio shared secret and the Loop QR code URL are stored encrypted with an AES-256-GCM key in the Android Keystore that needs no unlock, so background downloads, alarms and remote commands keep working while the phone is locked. App data is left out of cloud backup and device-to-device transfer; the key never leaves the device, so a moved copy could not be decrypted anyway, and a secret that cannot be decrypted reads as empty. Import/export and QR codes carry the plain values, as on iOS. Code: `storage/SecretCipher.kt`, `storage/StorageValue.kt` (`secret`), `storage/Storage.kt`, `res/xml/data_extraction_rules.xml`, `AndroidManifest.xml`. iOS: `Storage/Storage.swift` (plain UserDefaults).
- **Plain HTTP**: release builds allow only encrypted connections, as iOS does with App Transport Security and no exceptions; a `http://` Nightscout address with a host name does not connect. Debug builds also reach 127.0.0.1, localhost and 10.0.2.2 over HTTP for local test servers. Code: `res/xml/network_security_config.xml`, `src/debug/res/xml/network_security_config.xml`. iOS: `LoopFollow/Info.plist` (no `NSAppTransportSecurity`).
- **Alarm notification permissions**: Background Refresh settings show whether notifications (including the Alarms channel) and, on Android 14 and later, full-screen alerts are allowed, each with a button to its system page; Alarm Settings shows the same rows while one is denied, and while an enabled alarm exists and one is denied a warning banner is shown once per app run (dismissing it removes it). The alarm sound plays without them. iOS has no full-screen alert permission. Code: `alarm/AlarmPermissions.kt`, `ui/settings/SettingsScreens.kt` (`alarmPermissionSection`), `ui/alarms/AlarmSettingsScreen.kt`, `engine/BannerManager.kt` (`BannerSource.AlarmPermissions`), `ui/MainActivity.kt` (`onResume`). iOS: none.
- **Unrestricted battery use**: Android can pause a battery-optimized app in the background, which delays downloads and alarms. Onboarding has a step after notifications, shown only while LoopFollow is battery-optimized, that opens the system request to run without battery restrictions; Background Refresh settings show the state with a button to the same request, and while an enabled alarm exists and the app is still optimized, the one-time Home banner says so (after the notification and full-screen cases). iOS has no such setting. Code: `alarm/AlarmPermissions.kt` (`batteryUnrestricted`, `updateBanner`), `ui/onboarding/OnboardingModel.kt` (`OnboardingStep.BATTERY`), `ui/onboarding/OnboardingScreen.kt` (`BatteryStep`), `ui/settings/SettingsScreens.kt` (`BackgroundRefreshSettingsScreen`). iOS: none.
- **Log cleanup**: log files older than yesterday are removed at process start and again a minute after each midnight, since the background service can keep one process running for days. Code: `engine/MainEngine.kt` (`scheduleLogCleanupTask`). iOS: `Application/AppDelegate.swift` (launch only).

## Not available on Android

- **Apple Watch, CarPlay, Dynamic Island, app badge, calendar and contact-image tricks**: iOS-only system features. The onboarding completion screen leaves out the "Contact image" tip for the same reason. Code: `ui/onboarding/OnboardingScreen.kt` (`CompletionStep`). iOS: `Onboarding/Steps/CompletionStepView.swift`.

## Telemetry

- **Install identifier**: `idfv` is a random UUID that LoopFollow creates on first use and keeps in app storage (`telemetryInstallId`); it resets when the app is uninstalled or its data is cleared (app backup is off). Android has no per-vendor identifier. Code: `helpers/Telemetry.kt` (`installId`, `buildPayload`). iOS: `Helpers/Telemetry.swift` (`buildPayload`).
- **Device, platform and OS fields**: `device` is `Build.MANUFACTURER Build.MODEL` (e.g. `Google Pixel 8`), prefixed with `Simulator ` on the emulator, which is the prefix the telemetry server excludes from analysis; `platform` is `Android`; `osVersion` is `Build.VERSION.RELEASE`. Code: `helpers/Telemetry.kt` (`hardwareIdentifier`, `buildPayload`). iOS: `Helpers/Telemetry.swift` (`hardwareIdentifier`, `detectPlatform`).
- **Fields left out**: no `isTestFlight`, `contactEnabled` or `calendarEnabled`; Android has no TestFlight builds and no contact or calendar integration. Code: `helpers/Telemetry.kt` (`buildPayload`). iOS: `Helpers/Telemetry.swift` (`buildPayload`).
- **Build identity**: `appVersion` is the version name and `buildDate` the date the APK was built (`BuildConfig.BUILD_DATE`). The after-update ping compares version name, version code and build date (`telemetryLastSentBuild`), since the Android build carries no commit SHA. Code: `helpers/Telemetry.kt` (`buildIdentifier`), `app/build.gradle.kts`, `storage/Storage.kt`. iOS: `Helpers/Telemetry.swift` (`buildShaChangedSinceLastSend`), `Storage/Storage.swift` (`telemetryLastSentSha`).
- **Retry floor**: the next scheduled run is never less than a minute away, so a send that keeps failing while the daily ping is overdue retries once a minute. Code: `helpers/Telemetry.kt` (`scheduleRecurring`). iOS: `Helpers/Telemetry.swift` (`scheduleRecurring`).
- **Startup without a readiness wait**: the cold launch is recorded and the schedule started from `Application.onCreate` on every process start; the app is not direct-boot aware, so preferences are always readable then. Code: `LoopFollowApplication.kt`, `helpers/Telemetry.kt` (`start`). iOS: `Application/AppDelegate.swift` (`StorageReadiness.whenReady`).
- **Debug telemetry endpoint**: debug builds can send check-ins to a local test server (`debugTelemetryURL`, a full URL); release builds always use lf.bjorkert.se. Code: `helpers/Telemetry.kt` (`endpoint`). iOS: none.
- **Consent prompt**: a full-screen page shown over the app after onboarding while the decision is not made, left only through its two buttons (Back does nothing, or closes "What's sent"); the notification permission request follows once it is decided. Code: `ui/settings/TelemetryScreens.kt` (`TelemetryConsentScreen`), `ui/MainActivity.kt`. iOS: `Helpers/Telemetry.swift` (`TelemetryConsentView`), `Application/MainTabView.swift`.
- **Texts**: the consent and onboarding texts say "Android version" where iOS says "iOS version"; the Privacy page describes the install identifier, manufacturer and model and Android version, leaves out TestFlight and the calendar/contact flags, and names `helpers/Telemetry.kt` as the source. Code: `ui/settings/TelemetryScreens.kt`, `ui/onboarding/OnboardingScreen.kt` (`TelemetryStep`). iOS: `Helpers/Telemetry.swift` (`TelemetryPrivacyView`, `TelemetryConsentView`), `Onboarding/Steps/TelemetryStepView.swift`.

## Remote commands

- **"Command Sent" text**: says the result shows once it is uploaded to Nightscout; no confirmation notification reaches Android. Code: `remote/RemoteSupport.kt` (`RemoteCommandMessage.SENT`). iOS: `Remote/RemoteCommandMessage.swift`.
- **Number entry while focused**: a value set from outside (quick pick, recommendation) replaces a focused field's text, so the number on screen is the number that would be sent; typed text is never rewritten. Send buttons, Enact and Save as Preset leave the field first, and when that guardrail check rejects the typed value the action stops so its error is shown. Code: `ui/remote/RemoteComponents.kt` (`QuantityInputRow`, `rememberGuardedAction`, `BottomActionButton`), `ui/remote/TrioRemoteScreens.kt` (temp target). iOS: `Helpers/TextFieldWithToolBar.swift`.
- **Debug APNs endpoint**: debug builds can send pushes to a local test server (`debugApnsBaseURL`); release builds always use Apple's servers. Code: `remote/APNS.kt` (`APNSEnvironment`). iOS: none.
- **No return-notification block**: no Trio command carries `return_notification` and no Loop command carries `encrypted_return_notification`. Android cannot receive APNs, and Trio, Loop, the Loop remote carb edit customization and the Loop profile customization all apply a command without it (they skip the reply and still post failures as Nightscout notes). Code: `remote/TrioRemote.kt` (`payload`), `remote/loop/LoopAPNSService.kt` (`LoopAPNSCommands`). iOS: `Remote/TRC/PushNotificationManager.swift`, `Remote/LoopAPNS/LoopAPNSService.swift` (`sendConfirmedCommand`).
- **Meal and carb edit/delete and profile commands without a reply**: Trio meal edit/delete, Loop carb edit/delete and the Loop and Trio profile commands (activate, save, rename, delete, scheduled switches) are sent without waiting for the AID app's confirmation push. The sending screen shows "Command Sent" and returns to the list (edits return past the detail screen, profile edits and reviews to the screen they started from); a send failure shows as an alert, or for a meal or carb delete as a red line in the Remote actions section. There is no pending state, no "Waiting for Loop..." / "Another Profile Command Is Pending" button state and no reply or timeout alert. Code: `remote/loop/LoopCommands.kt`, `remote/profiles/ProfileRemote.kt` (`ProfileCommands`), `ui/treatments/TreatmentsScreen.kt` (`TreatmentDetailScreen`), `ui/remote/TreatmentEditScreens.kt`, `ui/remote/ProfileScreens.kt`. iOS: `Remote/RemoteCommandTracker.swift`, `Remote/Profiles/ProfileCommandFlow.swift`, `Treatments/TreatmentsView.swift` (`TreatmentDetailView`), `Remote/TRC/TRCMealEditView.swift`, `Remote/LoopAPNS/LoopCarbEditSheet.swift`, `Remote/Profiles/TherapyProfilesView.swift`, `Remote/Profiles/ProfileReviewView.swift`, `Remote/Profiles/ScheduledSwitchesView.swift`.
- **Early fetches after edits and deletes**: carb entry edits and deletes start the early Nightscout fetches used for new treatments and end when the carb data changes. The Treatments list reloads once the fetches after a meal or carb edit or delete finish, where iOS reloads when the confirmation push arrives. The early profile fetches after a profile command end only when the uploaded profiles show the change, or after the last fetch; iOS also ends them on a refusal in the reply push. Code: `remote/RemoteCommandRefresh.kt` (`Change.CarbEntry`, `Change.Profile`, `carbEntryRefreshes`), `ui/treatments/TreatmentsScreen.kt`. iOS: `Remote/RemoteCommandRefresh.swift` (`profileCommandAnswered`), `ViewControllers/MainViewController.swift` (`handleRemoteMealCommandDidComplete`), `Treatments/TreatmentsView.swift`.
- **Profile command size**: the review shows the size of a Trio command once the shared secret is set, since the command is encrypted with it, and the size of a Loop command always; neither carries a reply block, so no LoopFollow APNs credentials are needed. Code: `ui/remote/ProfileScreens.kt` (`sizeFooter`), `remote/TrioRemote.kt` (`profileCommandPushSize`). iOS: `Remote/Profiles/ProfileReviewView.swift` (`sizeFooter`), `Remote/Profiles/ScheduledSwitchesView.swift`.
- **Profile and scheduled switch editors**: a value is picked from a menu that opens at the current value, with −/+ to step to the next allowed value, where iOS uses wheel pickers; an expanded row has a Remove Time button and the Scheduled Switches list a Pause or Resume button per start, where iOS uses swipe actions; a start in the editor is deleted from its own screen, and its time is picked in an Android time dialog. The edit, rename and scheduled switch flows are pushed screens instead of sheets, so the system back gesture works as Cancel. Code: `ui/remote/ProfileScreens.kt` (`OptionStepperRow`, `profileValuesSection`, `scheduledSwitchesSection`, `ScheduledSwitchEntryScreen`). iOS: `Remote/Profiles/ProfileValuesEditor.swift`, `Remote/Profiles/ScheduledSwitchesView.swift`, `Remote/Profiles/ProfileEditorSheet.swift`.
- **Edit time picker**: the meal and carb edit forms use Android date and time dialogs, clamped to the same range as the iOS inline DatePicker. Code: `ui/remote/TreatmentEditScreens.kt` (`pickDateTime`). iOS: `Remote/TRC/TRCMealEditView.swift`, `Remote/LoopAPNS/LoopCarbEditSheet.swift`.

## Onboarding

- **Notifications step**: shown while the notification permission is neither granted nor asked for before, since Android has no "not determined" state to query. Outside onboarding, the permission is asked for once on launch. Code: `ui/onboarding/OnboardingScreen.kt` (`notificationsUndecided`, `RequestNotificationsIfUndecided`). iOS: `Onboarding/OnboardingViewModel.swift`, `Application/MainTabView.swift`.
- **Day/night times and absorption pickers**: Android time and date dialogs replace the iOS wheel pickers, with the same allowed values. Code: `ui/onboarding/OnboardingScreen.kt`, `ui/remote/LoopRemoteScreens.kt`. iOS: `Onboarding/Steps/GeneralAlarmsStepView.swift`, `Remote/LoopAPNS/LoopAPNSCarbsView.swift`.
- **Sensor and pump change seeds**: the alarm threshold is hours of warning before the sensor lifetime or the 3-day pump limit ends, so the seeds keep the alarm default (12 hours) and the step shows "Remind before" in hours, plus the sensor lifetime in days. iOS seeds 10 and 3 into the same field and labels them "Remind after" days. Code: `ui/onboarding/OnboardingModel.kt` (`defaultSeedAlarms`), `ui/onboarding/OnboardingScreen.kt` (`SeedControls`). iOS: `Onboarding/OnboardingViewModel.swift`, `Onboarding/Steps/AlarmsStepView.swift`.

## Statistics

- **Temp basal entries**: kept for the whole app session, so reopening the screen with otherwise complete data still shows Actual Basal. Code: `engine/stats/StatsDataService.kt`. iOS: `Stats/StatsDataService.swift`.

## Import/Export

- **Nightscout re-check after import**: after importing Nightscout settings the app verifies the site and refreshes, so the new site is picked up at once. Code: `ui/settings/importexport/ImportExportSettingsViewModel.kt`. iOS: `Settings/ImportExport/ImportExportSettingsViewModel.swift`.
- **QR scanner**: QR codes are read with ML Kit's on-device barcode model from a 1080p CameraX stream, which reads the dense remote settings code (APNs key included) from a phone screen. Code: `ui/components/QRScanner.kt`, used by `ui/settings/importexport/ImportExportSettingsScreen.kt`, `ui/onboarding/ConnectImportStep.kt` and `ui/remote/RemoteSettingsScreen.kt`. iOS: `Helpers/Views/SimpleQRCodeScannerView.swift`.

## Ongoing notification

- **Live Activity as the ongoing notification**: the Live Activity card is the content of the background service's ongoing notification and is redrawn locally on each refresh. There is no Dynamic Island, push-to-update, 8-hour renewal or "Tap to update" overlay, since Android has no Live Activities. Code: `liveactivity/LiveActivityNotification.kt`, `service/LoopFollowService.kt` (`OngoingNotification`). iOS: `LoopFollowLAExtension/LoopFollowLiveActivity.swift`, `LiveActivity/LiveActivityManager.swift`.
- **On by default**: "Enable Live Activity" starts on, because the ongoing notification is posted whenever the background service runs. Code: `storage/Storage.kt` (`laEnabled`). iOS: `Storage/Storage.swift` (`laEnabled`).
- **Off means minimal, not gone**: with the Live Activity off the notification stays with only the app name and a short line, since the foreground service that keeps alarms running requires a notification. Code: `service/LoopFollowService.kt` (`buildOngoing`), `liveactivity/LiveActivityNotification.kt` (`applyMinimal`). iOS: `LiveActivitySettingsView.swift` (ends the activity).
- **Collapsed form**: the collapsed notification shows BG and arrow in the range color plus delta with unit, or "⚠️ Not Looping", as in the Dynamic Island expanded leading region; Android notifications always have a collapsed form. Code: `liveactivity/LiveActivityNotification.kt` (`collapsed`). iOS: `LoopFollowLiveActivity.swift` (`DynamicIslandLeadingView`).
- **Reading age in the header**: the notification header shows the system-maintained age of the reading next to the app name, alongside the card's "Last Update" time. Code: `liveactivity/LiveActivityNotification.kt` (`apply`). iOS: none.
- **Stale reading struck through**: a reading 12 minutes or older is struck through, as in the home screen BG display, since the notification stays posted for as long as the service runs. Code: `liveactivity/LiveActivityNotification.kt` (`glucoseText`). iOS: `LoopFollowLiveActivity.swift` (`LockScreenLiveActivityView`).
- **Card background**: the range tint opacities are blended over a fixed dark base into an opaque color, since a notification has no translucent lock-screen material. Code: `liveactivity/GlucoseSnapshot.kt` (`LAColors`). iOS: `LoopFollowLiveActivity.swift` (`LAColors.backgroundTint`).
- **Settings screen**: the footer describes the ongoing notification, and the APNs credentials warning and the "Grid Slot - CarPlay / Watch" section are left out, since the card is updated locally and has no CarPlay or Watch form. "Restart Live Activity" redraws the notification. Code: `ui/settings/LiveActivitySettingsScreen.kt`. iOS: `LiveActivitySettingsView.swift`.
- **Trend arrow icons**: the card draws the trend with arrow icons, as the home screen does; the notification font renders the arrow characters as a short dash. An unknown trend shows "–". Code: `liveactivity/LiveActivityNotification.kt` (`setTrendArrow`), `res/drawable/la_arrow_*.xml`. iOS: `LoopFollowLAExtension/LoopFollowLiveActivity.swift`.
- **Status bar chip (Live Update)**: on Android 16 and later, with "Show in Status Bar" on (the default), the notification is a Live Update: glucose and trend in a status bar chip, as the Dynamic Island compact leading region shows them, and the card kept expanded at the top of the shade and lock screen. Android promotes only notifications without custom views, so the card then uses the standard layout: BG, arrow and delta as the title and the grid slots, override, temp target, CGM state and "Last Update" as text lines. A stale reading shows as "⚠ value" in the chip, which has no strikethrough. The card posts on its own channel with default importance and no sound or vibration, so phones that hide silent notifications on the lock screen still show it. Code: `liveactivity/LiveActivityNotification.kt` (`applyLiveUpdate`, `LiveUpdate`), `service/LoopFollowService.kt` (`CHANNEL_LIVE_UPDATE`), `ui/settings/LiveActivitySettingsScreen.kt`. iOS: `LoopFollowLiveActivity.swift` (Dynamic Island).
- **Glucose widget**: a home and lock screen widget shows glucose, trend, delta and the reading's age (a running count), on the range-colored card background. Android widgets have no refresh budget, so it is redrawn with every refresh of the notification. Code: `widget/GlucoseWidget.kt`, `res/layout/widget_glucose.xml`. iOS: none.
- **Screensaver**: "LoopFollow Glucose" can be chosen as the phone's screensaver, shown while it charges: the time, glucose in the range color, trend, delta, age and Not Looping or CGM state, shifted a little each minute against burn-in. Code: `dream/GlucoseDream.kt`, `res/layout/dream_glucose.xml`. iOS: none.

## Graph

- **Basal schedule before its first entry**: when the current time is before the first scheduled basal entry of the day, the schedule continues from the previous day's last entry. iOS steps past the start of the schedule array there. Code: `engine/ProfileTask.kt` (`updateProfile`). iOS: `Controllers/Nightscout/Profile.swift`.

## Home

- **BG and info table widths**: the BG block takes at least 55% of the row and the info table the rest, up to 250 dp, so the BG reading stays large on narrow phones and with larger text. iOS gives the table 160 to 250 points and the BG view the remaining width. Code: `ui/home/HomeScreen.kt` (`BGAndInfoRow`). iOS: `ViewControllers/MainHomeView.swift`.
